# IgniteAuth v0.9 Milestone

## Status

IgniteAuth v0.9 has reached its first working system integration milestone.

The backend now proves that IgAPI can send a scoped control-plane request into the IgniteAuth engine, receive an allow/deny decision, and return that decision back through the API boundary.

## Proven Flow

```text
IgAPI
  -> ControlPlaneCall
  -> IgniteAuth.Results.ControlPlaneDecision.DecideAsync()
  -> IgniteAuth.Processors.ControlPlaneProcessor.ProcessAsync()
  -> IntentValidator
  -> CommandValidator
  -> IntentCommandMapper
  -> ControlPlaneResult
  -> IgAPI ControlPlaneResponse
```

## Working APIs

### GET Reference System

Returns the current reference system model:

- Reference system identity
- Subsystems
- Policy definitions
- Allowed intents
- Allowed commands
- Allowed targets

This endpoint currently proves static/reference data loading.

### POST Decide

Accepts a scoped control-plane call and returns a decision result.

Example successful response:

```json
{
  "cpcId": 1,
  "intent": "IntentHash1",
  "command": "ReadModel",
  "subSystem": "ModelService",
  "decision": "Allow",
  "reasonCode": "ALLOW_VALIDATED",
  "message": "Intent, command, and intent-command mapping validated.",
  "timeStamp": "2026-09-28T18:53:12.6211042Z"
}
```

## Architecture Boundary

The system now follows this ownership model:

| Layer | Owns | Examples |
| --- | --- | --- |
| IgAPI Controllers | HTTP routes and API behavior | ControlPlaneController |
| IgAPI Models | Request and response DTOs | ControlPlaneCall, ControlPlaneResponse |
| IgniteAuth Interfaces | Contracts between IgAPI and IgniteAuth | IControlPlaneDecision, IControlPlaneProcessor |
| IgniteAuth Data | Loaded policy/hash/config data | IntentHashes, CommandData, IntentCommandMapping |
| IgniteAuth Validators | Individual checks | IntentValidator, CommandValidator, IntentCommandMapper |
| IgniteAuth Processors | Decision orchestration | ControlPlaneProcessor |
| IgniteAuth Results | Verdict and result shape | ControlPlaneResult, ControlPlaneDecisionVerdict |

## Core Security Model

The control plane is not directly driven by the client.

```text
Client
  -> asks the system to perform an action

System / IgAPI
  -> authenticates the user
  -> scopes the operation
  -> builds ControlPlaneCall

IgniteAuth
  -> evaluates intent, command, subsystem, and mapping
  -> returns Allow or Deny

System / IgAPI
  -> executes only if allowed
```

Golden rule:

```text
Client requests a system action.
The system creates the ControlPlaneCall.
The control plane decides.
```

## Current Decision Logic

The v0.9 processor follows deny-by-default behavior:

1. Reject empty or invalid raw payload.
2. Validate intent for subsystem.
3. Validate command for subsystem.
4. Validate intent-command mapping.
5. Return Allow only if every validation passes.

Failure states include:

- SCHEMA_INVALID
- INTENT_INVALID
- COMMAND_INVALID
- ICT_MAPPING_FAILED
- DENY_DEFAULT

Success state:

- ALLOW_VALIDATED

## Current Lessons

The main difficulty was not the architecture. The main difficulty was dependency binding:

- IgAPI needed to call the IgniteAuth bridge.
- ControlPlaneDecision needed IControlPlaneProcessor.
- ControlPlaneProcessor needed validators.
- Validators needed data loaders.
- Data loaders and validators needed secret/env handling.

Once dependency injection and secret handling were wired correctly, the design held.

## v0.9 Meaning

v0.9 is not final product polish.

v0.9 means:

- The reference system model exists.
- The control-plane request path exists.
- The deny-by-default processor exists.
- Validator-based decisioning works.
- IgAPI and IgniteAuth are connected.
- The system can return a real allow/deny decision.

## Next Steps Toward v1.0

1. Add CorrelationId to the decision response.
2. Add decision audit/history storage.
3. Add target-level validation.
4. Align ReferenceSystem policies with the same source used by validators.
5. Add system configuration and data loader services.
6. Add frontend trigger for control-plane calls.
7. Add richer reason metadata for denied decisions.
8. Add tests for allow, invalid intent, invalid command, and invalid mapping.

## Milestone Statement

IgniteAuth v0.9 proves the first complete control-plane decision loop:

```text
System request in.
Policy validation runs.
Decision comes out.
```

This is the point where IgniteAuth stops being only a concept and becomes a working backend system.
